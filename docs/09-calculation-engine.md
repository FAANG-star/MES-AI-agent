# 09 — Calculation & Rule Engine (Day 6)

[`agent/derive.py`](../backend/app/agent/derive.py)
Tests: 47 new, 278 total.

Day 5 collected facts. Day 6 turns them into the conclusions the factory manager
actually asked for — the capacity number, the named bottleneck, the fit-to-run
verdict, the ranked attention list, the quantified shortfall.

This is the layer acceptance criterion 4 is about: *"production quantities are
generated by deterministic calculation functions rather than invented by the
LLM."*

## 1. Pure functions, and why that matters here

Every function in `app/engine/` takes typed inputs and returns a typed result.
No database, no language model, no clock. That is not tidiness for its own sake:

- a test can pin an **exact integer** against a fixed dataset, so "reliable
  calculation" is a claim with a test behind it;
- the same function can be run against the SQL oracle and required to agree;
- the model cannot reach it. The LLM chooses *which* question is being asked;
  the engine decides *what the number is*.

The step is recorded in the trace as `kind: "engine"` with the note *"no
language model is involved in this step"*, and `tool_call_count` excludes it —
a calculation is not a tool call, and the audit trail should not blur the two.

## 2. Capacity

The algorithm is exactly [`02-architecture.md` §5](02-architecture.md). Two
implementation choices are load-bearing.

**Decimal, not float.** `db/verify.sql` computes the same numbers over
PostgreSQL `NUMERIC`. A float landing on 856.9999999 instead of 857 would break
that agreement at a boundary, so the engine works in `Decimal` and floors
explicitly.

**The floor is applied per machine, then summed.** A machine cannot produce a
fraction of a part, so three machines with five spare minutes each waste that
slack individually — pooling the hours first would invent parts that no machine
can make. A test pins a case where the two differ (3 × 20 min at a 7 min cycle:
6 parts, not 8).

The result carries its own working:

```
cycle time 3.5 min/part
CNC-01: 72 planned − 0 maintenance = 72 h → floor(72 × 60 ÷ 3.5) = 1234 parts
CNC-02: 72 planned − 0 maintenance = 72 h → floor(72 × 60 ÷ 3.5) = 1234 parts
CNC-03: 72 planned − 22 maintenance = 50 h → floor(50 × 60 ÷ 3.5) = 857 parts
machine capacity = 1234 + 1234 + 857 = 3325 parts
material capacity = floor(9600 ÷ 1) = 9600 parts
final = min(3325, 9600) = 3325 parts (machine-constrained)
```

That line-by-line `formula` is what lets the answer justify itself on screen
rather than asking to be believed.

**Preconditions refuse; they never estimate.** A missing cycle time, a missing
material quantity, uncounted stock, or no eligible machine raises
`CapacityUnavailable` carrying the field name — the same contract the retrieval
tools use for a NULL, so the refusal reaches the user naming
`parts.cycle_time_min` whether it was caught at step 1 or step 5.

## 3. Bottleneck

A sort, plus two judgements that matter more than the sort.

**A tie is not a bottleneck.** If two eligible machines share the lowest
effective hours, nothing distinguishes them and naming one would be arbitrary.
The engine returns "no single bottleneck" and says which machines are level.
This is the honest answer on the last working day of the week — the case
[`05-seed-data.md` §5](05-seed-data.md) documents.

**Material outranks machines.** When stock is the binding constraint the
limiting factor is not a machine at all, and naming CNC-03 would point the
manager at the wrong problem. C15 exercises this branch on every weekday.

## 4. Machine-condition rules

Thresholds are **not** in the code. They are read from `rule_thresholds` and
passed in (ADR-4), so a plant can retune a limit without a deployment and every
verdict cites the row it was compared against:

> Spindle temperature: 52 °C — Normal (below the 70 °C limit).

Three rules the demo depends on:

| Rule | Why |
|---|---|
| A missing reading is `not_assessable`, never "healthy" | Silence from a sensor is not a passing grade |
| `maintenance` status, or maintenance active today, overrides sensors | A machine under the spanner cannot produce however good its readings are |
| Attention ranks by breach count, then by **relative** severity | 3.1 mm/s against a 2.5 limit is 24 % over; 72.5 °C against 70 is 3.6 % — the same count, very different urgency |

Utilisation is deliberately excluded from the attention score. It is bottleneck
context, not a condition fault, and `db/verify.sql` ranks the same way.

## 5. Production analysis

Every percentage in the S4 answer is derived here, and none is stored:

```
shortfall      = planned − produced          = 35
pct_below_plan = 100 × 35 / 250              = 14.0 %
reject_rate    = 100 × 8 / (215 + 8)         = 3.6 %
parts_lost     = 2.1 h × 60 / 3.5 min        = 36 parts
```

That last conversion is what turns a list of numbers into an explanation.
Downtime in hours and rejects in units are not comparable until both are
expressed in parts — only then can the factors be **ranked by quantified
impact** rather than listed in whatever order they were checked. On the seeded
incident the downtime works out to 36 parts against a 35-part shortfall, which
is why the answer can say the downtime accounts for the miss and mean it.

This forced one change to the Day-4 plan: `production_analysis` now fetches
`get_part_information` first, because the cycle time is what makes the
conversion possible. It is **not** declared as `requires` — a missing cycle time
leaves the downtime unquantified rather than refusing the analysis. The same
field is mandatory for capacity and optional here, which is exactly what the
per-step `requires` mechanism is for.

## 6. Two implementations, one specification

`db/verify.sql` has computed capacity, bottleneck, health ranking and
plan-versus-actual in SQL since Day 2. The engine now computes the same things
in Python. [`test_engine_oracle.py`](../backend/tests/test_engine_oracle.py)
runs both over the **live seeded factory** — not a fixture — and requires exact
agreement.

That cross-check earned its place immediately. It caught a real divergence in
the attention ranking: for machines with no breach, SQL ordered by how close the
worst reading sat to its limit, while Python treated them all as equal. SQL's
order is the more useful one — 68 °C deserves more attention than 52 °C — so the
engine was changed to match.

It also surfaced a corner the specification never covered: a machine whose
sensor cannot be read has an *unknown* breach count, and SQL's `NULL`
propagation happened to sort it last. Sorting "unknown" below "known healthy" is
the wrong instinct for a maintenance list, so **both** sides now apply the same
deliberate rule — a machine that cannot be fully assessed ranks above one known
to be healthy. The decision is now written down instead of being an accident of
NULL handling.

## 8. What Day 7 picks up

The numbers are right; the prose around them is still assembled deterministically
from step summaries. Day 7 adds the validator and the explainer: the local model
writes the answer, and every numeric token in it must appear in the tool results
or the engine output, or the answer is regenerated once and then downgraded.

The engine is what makes that check possible — there is now a definitive set of
numbers to check the model's prose against.
